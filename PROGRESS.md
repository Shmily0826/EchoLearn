Measured before the fix, driving real playback of a synthetic 200-cue lesson: **6 scroll advances across 15 cues**, with the row's offset climbing 285 → 401 px between jumps. A new E2E pins the user-visible contract — 40 single-cue steps must produce a scroll increase on at least 80% of them and leave the active row on screen — and it was falsified against the old listener, which produces **7 of 39**. Two probe bugs found on the way and recorded rather than hidden: the first synthetic WAV was 40 s long against a 2557 s subtitle so "seeking" was meaningless, and a 1000 Hz WAV is rejected outright by Chromium (`MEDIA_ERR_SRC_NOT_SUPPORTED`, duration `NaN`) while 8000 Hz loads; and the first falsification attempt silently did nothing because the replacements were written with `\n` against CRLF files — the same line-ending trap this repository has now hit three times. ## CURRENT SNAPSHOT — 2026-09-21 (auth data lifecycle & AI cache trust, PRODUCTION VERIFIED)

- **`ECHO_AUTH_DATA_AND_AI_CACHE_SAFETY_V1` (implemented 2026-09-20, SHIPPED 2026-09-21 as `b469bd4`; branch `agent/auth-data-ai-cache-safety` off `b928ee8`, PRs #12 and #13).** Account deletion is now sequenced so a failed step cannot destroy the next one: prove identity, then delete cloud data with every failure propagated, then `deleteUser`, then purge the device (localStorage study data, both sync-marker sets, the GitHub PAT + gist metadata, and every IndexedDB audio Blob via `deleteDatabase`). Before this, the cloud and local wipes ran BEFORE `deleteUser`, so a `requires-recent-login` failure could leave the account alive with the learner's data already gone, and `Promise.allSettled` swallowed cleanup failures. Two closures from supervisor review: the cloud learning-data removal is now a **single batched write** (Firestore commits a batch all-or-none, so a mid-cleanup failure cannot leave half a library), and where the cloud documents would be the learner's **only** copy the deletion is **refused** with export guidance rather than performed — no pure-client ordering can make "cloud deleted, account survived" recoverable, so the strict no-data-loss-on-failure AC is recorded as a design limitation rather than claimed as fixed. Feedback became deletable by nesting the uid in the path (`feedback/{uid}/messages/{id}`, `list` capped at 50 with the client mirroring that limit), because no owner-side rule can reach flat documents whose autogenerated ids the client never held. The shared AI cache lost its client-side trust problem: `aiCache/{writerUid}/analyses/{key}` is verified-owner-only for **both** reads and writes, and the legacy public `aiAnalyses/{key}` corpus is frozen by rules *and* no longer read by the client — immutability now does not make past writes trustworthy, since any signed-in or unverified client could perform them (the reproduction showed an *unverified* session's write becoming the served content). Cross-user HITs therefore stop accruing and legacy-cached analyses are re-paid once per learner; restoring full sharing costs a service-account decision and is recorded as one, not smuggled in.
